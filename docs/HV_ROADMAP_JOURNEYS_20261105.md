# Private journey history — roadmap #11

Local implementation begins with `journeyStore` and its accepted Legacy snapshot integration. Collection requires both `JOURNEY_HISTORY_ENABLED=1` and a per-player opt-in. The rollout flag is off by default. There is no public endpoint or browser consent control yet, and no production data has been collected by this work.

Preferences use optimistic revisions. Deleting history also disables collection and preserves a consent cutoff so delayed samples cannot recreate it. Renewed opt-in begins a new collection epoch. Historical points are private to the supplied authenticated actor at the future API boundary; no cross-account list method exists.

Storage retains at most 10,000 points per player for up to 30 days, with at least 15 seconds between samples in a continuous life. Reads return at most 500 points and an exclusive timestamp cursor. Expired points are excluded from reads and pruned during accepted snapshots. When snapshots stop, physical cleanup waits for the next accepted snapshot; a separate scheduled cleanup remains necessary before rollout.

Only accepted Legacy snapshots feed collection. Life changes, gaps over two minutes and displacement above 40m/s break the route. Points represent observed samples, not exact distance or proof of death. Existing Legacy observation closure is deliberately not relabelled as death.

Local tests cover consent, deletion, late samples, account isolation, malformed/future/duplicate timestamps, route discontinuities and integration behind the rollout gate. Still required: bounded-read and storage-cap verification, stronger coordinate validation at the snapshot boundary, session-bound account APIs, consent/deletion UI, private map rendering, trustworthy death/event association, retention scheduling, staging and production verification. Discovery (#10) and recap (#12) remain separate incomplete requirements; no rewards or game commands are introduced.

Storage and coordinate validation follow-up: accepted snapshots now reject empty strings, booleans, arrays and objects as coordinates rather than coercing them to zero. Numeric coordinate strings remain supported. Tests verify a 10,001st sample retains only the newest 10,000 points, all paginated reads are unique and complete, and another account remains untouched. This closes the bounded-read/storage-cap and snapshot-coordinate checks listed above; account APIs, UI and release gates remain outstanding.

Private account APIs are now implemented at /api/journeys with settings, points, preference changes and explicit deletion. Every actor comes from the website session; internal automation calls require the website bearer token. Both deployment flags must be enabled on the website. Same-origin JSON and preview restrictions protect writes; JOURNEY_HISTORY_READ_ONLY=1 blocks preference mutations independently. Responses are private/no-store. An isolated two-server HTTP fixture verifies consent, account isolation, forged actor rejection, deletion, stale revisions, read-only behavior and disabled rollout. No browser controls exist yet, and this branch remains local.

The /journeys page now exposes consent, confirmed deletion, history refresh and older-page reads, with a profile link. Its map uses shared Gateway bounds from capabilities, groups observations by life ID and draws only connected samples. Out-of-bounds points are counted but not clamped onto the map. Distances are explicitly sampled rather than complete travel. Preferences default off, and read-only/guest/disabled states are covered in 1440px and 390px browser fixtures. The page does not persist private points in browser storage. End-to-end HTTP authorization still passes. Gameplay-event summaries, verified death provenance, scheduled cleanup and staging remain pending.

Retention scheduling now runs on Valley Legacy startup and its existing 15-second maintenance timer. Journey cleanup runs independently of event import and regardless of JOURNEY_HISTORY_ENABLED, so disabling new collection does not stop expiration. The local maintenance fixture verifies expired records disappear with no incoming snapshots and a deliberately broken combat import, while recent records remain. This requires the Valley Legacy service to be running/enabled; an offline service cannot erase disk records until it restarts. The earlier scheduled-cleanup implementation gap is closed; staging still needs to verify the real service lifecycle.

Missing-position continuity: invalid or absent coordinates now save a private timestamp-only gap marker for opted-in players. The next accepted location breaks the trail even when the missing interval was shorter than two minutes. Reopening the store preserves the break, and older samples cannot fill it. Deletion removes gap markers alongside points; retention expires them. Local tests cover service reinitialization, stale samples, subsequent normal continuity and deletion.

Observed-life closure provenance is now additive in vl_life_closures: not_observed, species_changed, observation_gap, growth_reset or combat_death. Combat-linked closures retain the immutable event ID. Historical closures without provenance remain unknown; no retrospective reason is guessed. A combat event can close the current observed life only when its timestamp is at/after the latest alive sample and within two minutes of that sample. Conflicting, distant or historical unmatched events remain stored without ending a newer/alive-observed life. This conservative association window is a local implementation guard, not verified in-game continuity. Owner Legacy responses include closure metadata; the journey summary UI and retrospective association/review remain pending.
